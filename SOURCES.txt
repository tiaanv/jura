EF533M V02.09 logs supplied by Tiaan, including AT challenge, TV espresso stages,
TF idle/ready payload and RT counter changes during a physical espresso test.
The retained six EF533 extras are scoped to that tested register layout.

Fresh native layer: nonblocking transport/session/controller, native ESPHome
entity integration, recipe validation, test fixtures and migration documentation.
There is no dependency on upstream MQTT discovery or its MQTT command router.
The runtime does not fetch model profiles from the network.

Differences from a direct upstream port:
* Read banks are derived from the profile's product codes, including above 0B.
* EF545 uses the documented 31/36 -> 12/13 counter remap with a direct fallback.
* Unknown/sentinel counts remain unavailable instead of being presented as zero.
* Valid TV keeps the session live while TF is absent; TF alerts can become stale
  independently of product progress. Idle read polls pause during operations.
* The command layer validates readiness, choices, ranges, steps and layout and
  never automatically retries a brew. A matching TV product confirms start.
* ESPHome entity allocation happens at code generation. Runtime model detection
  finalises names and visibility during setup, before native API discovery.

Known upstream database inconsistency:
EF562 / 2 Ristretti has temperature default 0, but its allowed choices are 1
(Normal) and 2 (High). The default recipe is rejected rather than silently
changed. Explicitly choose Normal or High for this product. All other active
product default recipes validate across the included 75 profiles.
